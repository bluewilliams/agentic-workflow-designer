# Branching strategy (large work onto branches, one per work item or chunk, planned at run time)

Context: no work item (direct session, director-relayed request: for large or epic-level work, an epic with many stories spanning repositories, split the work onto branches by logical chunk or by story. Director's constraints, in his words: "any team can be doing the work so there might be different prefixes", "on a brand new repo where there isn't an established pattern... look to other repos to infer what's best", "viewable in the explain step", "consider how this will play with those manual branch entries", "a way for the agents to know which repos are impacted", "make it the best it can be"). Branch: main. Status: current. Repo: agentic-workflow-designer.

## Current behavior

- **The lever** lives on the Output node, beside the delivery format, because delivery is already a function of that node. `Branching`: `single` (the shipped behavior, the Branch Name and Target Branch fields), `story` (one branch per work item, per repository: a story, a task, or a slice of a requirements document; the stored value stays `story`), `chunk` (work items grouped so each branch leaves every repository working). Absent keys read as `single`; a foreign value is dropped on load (`deserializeWorkflow`), so untouched saves keep their JSON. Two refinements under a strategy: `Branch pattern` (optional; tokens `{ticket}`, `{epic}`, `{story}`, `{slug}`, `{repo}`; empty means each repository's own convention) and `Integration branch` (`auto`: inferred per repository, default; `none`; `epic`: one epic branch per repository). The panel hides Branch Name under a strategy (and says a kept value plays no part) and relabels Target Branch to Base branch.
- **When it applies**: only on an Output node whose format creates branches (Commit or Pull Request). A strategy on any other format is inert and draws a validation warning. `workflowBranching()` is the one predicate every emission consults.
- **The Branch plan beat** (`branchPlanHint`, a shared hint in every format, since delivery is emitted in every format): discover the work items from an epic's child stories through the Atlassian MCP when it is available, from the pieces a requirements document lists, or as self-contained slices derived when it lists none; the chunk rule (the smallest set of stories that must land together to leave every repository working; a lone story is its own chunk); the repositories in scope are the Repositories list in the prompt, or the launch repository when the list is empty; map each unit to repositories from the story's components, labels, and named files and services, confirmed against the code; a unit that maps to no repository in scope is flagged, never guessed outside the list; a unit that spans repositories gets the same branch name in each; name branches by each repository's own convention, read from `git branch -r`, merge subjects, CONTRIBUTING, CLAUDE.md, `.claude/rules/`, and branch protection, recorded and applied per repository (teams differ, so repositories differ); a repository with no convention borrows from its nearest sibling in the run, then the run's most common convention, then `feature/{ticket}-{slug}`, saying which it borrowed; the director's pattern overrides everything when set; bases: a repository's branch in the Repositories list is that repository's base, the Output node's base applies to the rest, and Branch Name plays no part; the integration rule per choice; the plan is written down before anything exists (with memory on, as `b: {unit} | {repository} | {branch} | {base} | {target}` lines under the owner's own active entry in its OWN memory file, never edited in place, a corrected plan being new lines in a new entry, progress living on the task board, with one handoff line per builder in `shared.md` pointing there, so no status slot is touched and the monitor's parser sees nothing new; else in the plan output, with each builder's rows copied into its input only in the spawned formats; in the durable record when kept) and is shown to the director before any branch exists (the plan gate when Approve plan is on); the step that starts a unit creates its branch from its base; only the delivery pushes; never a commit to a base or integration branch; under a Commit delivery the beat never speaks of pull requests.
- **Per step** (`branchStepNote(node, spawned)`, at the six per-step sites the verification step hint uses): the plan owner is `branchPlanOwner()`, which IS the approval gate's plan owner (`approvalCheckpoint().owner`, or the last of a plan-owning group; memoized on the graph shape with the same sibling exclusion, per-repository lane shift, and unknown-role rule), so a rejection at the gate goes back to the step that wrote the plan; with none, the beat says the orchestrator writes the plan itself before the first builder and validation says so (info). In the spawned formats (Sub-Agents, Agent Teams) the owner's note carries the whole beat, since the top-level beat is not in front of a spawned step. Every builder role (`APPROVAL_BUILD_ROLES`) checks out its row's branch before changing files, confirms it, never commits to a base, never switches branches in a tree another step is using, and names the branch in its handoff; it is told where its rows are (memory on: the `b:` lines of the plan entry in `shared.md`; memory off and spawned: copied into its input by the orchestrator, whose card carries `branchOrchestratorNote`); a builder inside a per-repository lane owns every row for its repository, worked one at a time on that checkout; reviewers and verifiers get nothing. The sub-agent delivery discipline speaks per row too. No worktrees: units that touch one repository run one at a time on its checkout, a clone per branch only when the director prepared one, and the durable record and memory files always stay in the launch checkout (a worktree per branch would split the record across branches and lose the local rules).
- **Delivery** (`branchPlanDeliveryLines`): under a strategy, `prBlock` and `commitBlock` replace their one-branch lines with per-row steps: check out or create the row's branch from its base, commit that row's changes only, push each branch, one PR per branch into the row's target with the work item keys or titles in the body, the final epic-to-base PR where a repository has an epic branch, the manual-URL fallback. The Single-branch lines are untouched, byte for byte.
- **Approval brief** carries the branch plan (unit, repository, branch, base, PR target) when a strategy is configured, so names are corrected once at the gate. With Approve plan off, every surface says so plainly (the owner presents the plan and waits for a yes before any branch exists) and validation nudges the gate on; nothing claims an approval that did not happen. One base source: the strategy node's base, with the Repositories list's per-repo branch as that repository's base (the Repositories block says so under a strategy); the Base branch field shows for Commit as well under a strategy; two branch-creating Output nodes with different formats draw a warning and the Pull Request delivery wins. Chunk mode defines its tokens (`{ticket}` is the epic key, `{chunk}` the chunk slug; fallback `feature/{epic}-{chunk}`). **Explain**: a `Branching` row at workflow level, a `Branch plan step note` row per step (owner, builder, or the skip reason), and the Output node's `Branches` row describes the strategy, pattern, integration choice, and base. **SDK**: a comment banner only (the skeleton has no git mechanism). Help modal and README paragraphs.

## Why and scope

The existing fields take a name per branch, which is right for one branch the user already named and cannot scale to one branch per story per repository. The scalable input is a strategy, not names: the names live in the epic and in each repository's own history, which the agents can read and the director should see once. Scope: constants and helpers, a panel block, one shared beat, six per-step sites, two delivery variants, the brief clause, three Explain surfaces, one validation warning, an SDK comment, docs, one suite. Non-goals: no change to the Single-branch path, no new prefs, no change to the Repositories list or the Cross-Repo preset's lanes (they read the plan like any builder), no Live Run Monitor surface for the plan (a candidate for later).

## Approach and decisions

- A strategy on the Output node, not a workflow-level toggle or a sidebar section (rejected) - delivery is already a function of the Output node, and a branch is a delivery concern.
- Names planned at run time, never typed per repository (rejected: per-repo prefix fields) - seven repositories would mean seven fields nobody fills, and the convention is already written in each repository.
- Infer per repository, with an explicit evidence list and a fallback chain for a new repository (rejected: one org-wide default) - teams differ per repository; a new repository's nearest sibling is the best predictor, and the director corrects it once at the gate.
- The approval gate is the review moment (rejected: a new modal for the branch plan) - the gate already exists and already shows the brief; the plan is one more section of it.
- Branches only under Commit or Pull Request, only after approval (rejected: creating branches at plan time) - Leave Uncommitted stays exactly that.
- The manual fields keep their roles: Branch Name is the Single-branch control (hidden under a strategy, kept); the per-repo branch field is that repository's base; the Output base covers the rest.
