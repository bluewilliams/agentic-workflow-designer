# UI Design craft (visual identity in the brief, advisory design critique in the review)

Context: no work item (direct session, director-asked: should the UI Design preset be better at considering the product's current aesthetic and at making strong design decisions, or is it as good as it should be? Honest answer given: the preset is a conformance pipeline with no design judgment, which is the right default for work inside an existing product, but the Analyzer never looks at the running product and the Reviewer never asks whether the result is good design. Director's constraint: "I would like it to work in these cases as it does today" when the app cannot be run). Branch: main. Status: current. Repo: agentic-workflow-designer.

## Current behavior

- **Design System Analyzer** (`PROMPTS.designSystemAnalyzer`, shared by the UI Design preset and the auto-workflow UI shape): discovery step 9, "The product as it looks", runs only when browser tools are available and the app's local dev server is already running. It opens one or two screens that render the newest components read in step 5 (nothing is canonical yet during discovery), three turns at most for the whole step, finding and looking included, and reads them as a designer would: density, type scale in use, color roles, spacing rhythm, motion, voice of labels and empty states. Localhost only, the frontend template's safety line. It never starts a server, installs anything, or changes the environment to take the look. No running server, no browser tool, or screens not found within that budget: it skips the step, says so in the Brief with that reason, names the components instead of screens, and derives the identity from the tokens and the canonical component. "The Brief is complete without this step."
- The Brief gains a **Visual Identity** section (before Patterns to AVOID) and a handoff line that states its source: "from the running app" or "derived from code only" with the reason.
- **UI Implementer** (`PROMPTS.uiImplementer`): one style rule, match the Visual Identity section when the Brief has one (density, type scale, color roles, spacing rhythm, motion, voice of labels and empty states), and empty, loading, and error states are designed, not merely present: the Implementer is told everything the critique grades.
- **UI Reviewer** (`PROMPTS.uiReviewer`): a **Design Critique (advisory)** block after the standard code review: belonging, hierarchy and affordance, states as design, copy, restraint. Critique findings are Medium or Low, carry the Design category, and never make the verdict NEEDS REVISION on their own. A critique finding stays in the Design category even when it touches styling (a tokenized shadow the product does not use elsewhere is a Restraint note, not a violation); only a breach of the Brief's own rules is a Design System finding, and a real correctness or accessibility defect is filed under Correctness or Accessibility, never under Design System. With no Visual Identity section the Reviewer judges against the canonical component the Brief names (it has no Bash and five turns). The category list gains "Design"; the handoff gains "Design Notes" (non-blocking). The gating sentence ("Your default verdict is PASS ... only Critical or High findings make the verdict NEEDS REVISION") and "Design system violations are Critical severity" are unchanged.
- No new control in the designer. The existing UI Context box already steers the Analyzer (authoritative), so a line such as "keep the dense data-table feel, no motion" steers the aesthetic section too. The preset's node tools, shape, and the "UI review passed?" condition are unchanged. Help modal (Design Analyzer line, agent-type description) and the README preset line say what changed.

## Why and scope

Honest assessment given to the director: every step of the preset was about conformance (tokens, avoid list, canonical pattern, composition method). That protects the common case (a component that must belong to an existing product) and should stay the default; "be bold" or "contemporary" in a default prompt is the change most likely to make outcomes worse (trend-chasing, gratuitous motion). What a prompt can deliver is disciplined craft and a true picture of the product as it looks, which the Analyzer never had because it read code only. Scope: additive text in three templates, three docs lines, one test group. Non-goals: no Design Explorer step for net-new surfaces (a design discussion first, gated by the spec, where "unique when needed" would live), no second sidebar box for aesthetic notes, no browser tool added to the preset's tool list.

## Approach and decisions

- Conditional step, never a blocker (director constraint) - the step opens with "only when it can be done, never a blocker", carries the skip rule and the "complete without this step" sentence, and the Brief's source line makes the skip visible downstream instead of silent.
- Look only, never start (first draft let the Analyzer start the dev server with its documented command; the review round removed it) - starting a server is the one path by which a default run does more than today (a long-lived process, build caches, a postinstall), and it contradicted the help modal, the agent-type description, and the README, which all promised a look at an app that is already running. A read-only context specialist with ten turns does not reshape a developer's environment to take a look; the code-only path is the shipped behavior and is explicitly good enough.
- No App Under Test claim in the prompt (the first draft said the path "is the app") - the path lint names its consumers (App Explorer steps) and would have told the user nothing consumes the path while the prompt said otherwise; the Analyzer works in the repo it is run in.
- Advisory critique, severity-capped (rejected: critique findings as High) - the review gate's condition is "design-system compliant with no critical issues"; a taste finding must never send the Implementer around the loop by itself. A critique point that is also a real violation is filed as that violation, so nothing real is downgraded.
- Restraint as a critique item (rejected: "contemporary, eye-catching" language; the review round also replaced "distinctive moment ... earns its place" with plain words) - the product's own identity is the reference; if the spec asks for something the product does not do today, the reviewer says whether it is justified.
- Browser use as a suggestion inside the prompt (rejected: adding a browser tool to the preset's Design Analyzer node) - tool selections are suggestions never restrictions; the prompt says "if browser tools are available" and the tool list stays as it was, pinned by test.
- Both consumers optional ("when it has one") - a Brief produced by an older saved prompt, or by an Analyzer that skipped the step, still drives the Implementer and the Reviewer exactly as before.
