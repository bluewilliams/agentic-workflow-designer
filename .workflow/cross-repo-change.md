# Cross-Repo Change preset + the per-repository lane strategy

Context: no work item (direct session, director-requested after a parallel-coverage audit found one gap: a change that spans repositories - the app has a first-class Multi-Repo section but no preset that fans out BY REPOSITORY; the director asked that it reflect parallelism on the canvas like the other parallel presets without the builder reading the sidebar). Branch: main. Status: current. Repo: agentic-workflow-designer.

## Current behavior

- **Per Repository is a strategy of the Parallel node** (`strategy: 'per-repo'`, selectable in Node Configuration beside Wait for All / First Complete / Race). Its lane is every non-parallel node between the fork and its join (`perRepoLaneNodes`, revise back-edges skipped). At RUN time the orchestrator runs the lane once per repository listed under Repositories, lanes in parallel, instances named `{step-slug}-{repo-slug}` (repo slug = the repository folder name slugified, `repoSlugOf`), so the run monitor pools the instances under their step through the existing dynamic fan-out naming contract. With one repository (or none) the run uses a single lane on the working repository. Every lane finishes before the run continues.
- **The canvas stays static, and still shows every instance.** `renderParallelLanes` draws the dashed lane box around the whole lane even for a single-branch per-repo fork (other single-branch forks still draw none), captioned `parallel (per repository · N repos)` (`sequential` in single-session formats) - N is `getRepositories().length` read at render time as a display hint, never a shape input. `renderPerRepoInstances` then draws one SOLID node per extra listed repository below each lane step (the same shape, icon, label, and sublabel as a real parallel sibling, sublabel ending in the repository slug; the real lane step's sublabel carries the first repository), capped at 5 rows with a '+N more repositories' line beyond. Instances are render-time projections (class `node-instance`, `data-id` of the lane step): no state, nothing serialized, a left-click selects the lane step, selection outlines follow, and each instance wears its own live status dot from the monitor's `{step-slug}-{repo-slug}` entry (`monitorInstanceStatus`, quiet while idle-folded). Each instance row also gets the curves a real sibling would have (fork -> instance, instance -> instance along the lane, last instance -> join; class `connection-instance`, never interactive), drawn after the connections layer redraws. The lane box grows to hold the rows. The projection follows the list live: `onRepoChange` renders the canvas when a per-repo fork exists on the canvas AND the projection signature (repository count plus the slugs, `perRepoProjectionSig`) changed - so an add, a remove, or a slug-changing path edit redraws instances, the count caption, and the lane step's repo sublabel at once, while branch edits and slug-neutral path edits take the cheap prompt-only path and workflows without a per-repo fork never build the signature. The builder reads nothing from the sidebar.
- **Emission**: `perRepoLaneNote(forkId, sequential)` is emitted at the fork in the four prose formats (Workflow summary and Claude.ai in the one-repository-at-a-time wording, Sub-Agents and Agent Teams in the lanes-in-parallel wording); the Agent SDK export instead emits a real `_lane(repo)` coroutine that runs the lane steps in order per repository and gathers every lane concurrently; `perRepoStepHint(node)` rides all six prose per-step sites (beside the browser step hint, including both parallel-siblings loops; SDK per-step hints excluded by the format's minimal design). The step note reads "Runs as a per-repository lane". `strategyJoinPhrase('per-repo')` is defined. The other strategies emit byte-identically (pinned).
- **Explain**: the fork's Join strategy row names the lane semantics; each lane step gets a Per-repo lane row.
- **Cross-Repo Change preset** (`cross_repo`, More presets fold beside Platform Provisioning): Cross-Repo Change -> Contract Architect -> Skeptic gate ("Contract sound?", adversaryRole architect) -> Per-Repo Lanes (per-repo) -> Repo Implementer -> Repo Tester -> Collect -> Integration Verifier (mainline verifier) -> "Seam proven?" gate (Not verified loops to the lane) -> Reviewer (crossRepoReviewer) -> "Review OK?" gate -> Change Delivered. Six agents. Five bespoke crafts: `contractArchitect` (map the seam, write the contract ONCE with consumers, expand-contract ACROSS repositories, per-repo tasks, seam verification design), `repoImplementer` (one lane: this repository only, contract copied verbatim never adapted, never edits another repo, memory file `{step-slug}-{repo-slug}`), `repoTester` (contract-conformance tests from contract-derived fixtures, never mock the seam into agreement, honest about what needs other repos), `integrationVerifier` (prove consumer against producer, every contract item, literals character for character, compatibility window, evidence table item x repository with VERIFIED/MANUAL/FAILED), `crossRepoReviewer` (contract fidelity across repos first, each repository's own conventions second; deviation and out-of-repo edits always gate). Placeholder asks for the seam, the repositories, producer/consumers, contract constraints, acceptance criteria.

## Why and scope

Cross-repository changes fail at the boundary - two green repositories that disagree about a shape or a literal - and the roster had no shape for them although multi-repo is a first-class feature. Two designs were weighed: a builder that reads the Multi-Repo list and creates N nodes (rejected - breaks the invariant that the canvas is independent of the sidebar, and rots as repos change), or a run-time fan-out expressed as a Parallel strategy (chosen - static shape, existing naming contract, existing monitor pooling, and it generalizes to any user's parallel node). Scope: one strategy value with option, helpers, emission at seven sites, canvas, Explain, five crafts, builder, tile, placeholder, tests, README. Non-goals: no dynamic node creation, no sidebar reads in builders, no repo count in state.

## Approach and decisions

- Strategy over dynamic nodes (rejected: N implementer nodes from the repo list) - the canvas stays static and truthful, and the feature becomes a designer capability rather than a one-preset trick.
- Lane = chain to join (rejected: direct children only) - Implement then Test per repository is the realistic lane, and the box must enclose it.
- Verify the seam BEFORE review (rejected: review first) - the seam is the expensive failure and its fix loops to the lane; convention review follows a proven seam.
- Skeptic on the contract (rejected: none) - doubt early: a wrong contract is built against by every lane at once.
