# Team settings (one shareable file for the shop, the workflows, the agents, and the prompts)

Context: no work item (direct session; the director's organization is about to fork the designer for its teams, and he asked for the highest-value product improvement before that: a way for everyone to start from the same OTEL and Datadog telemetry settings, the same defaults, and the same company-standard workflows, agents, and prompts). Branch: main. Status: current. Repo: agentic-workflow-designer.

## Current behavior

- **Export, Team Settings**: a new item at the end of the existing Export menu in Workflow Management (no new button). `buildTeamSettings()` writes `{ format: 'awd-team-settings', version: 1, settings, workflows, agents, prompts }`. `settings` is the shop: Default Model, Effort, Delivery, the section pins, the three repo context path lists and the verification notes, the memory and record switches, the five MCP switches and the custom MCP notes, the two run gates, and the telemetry collector (enabled, endpoint, service, tags). **Machine-local values never travel**: the Repositories list, the App Under Test path, branch, access, the UI Context notes, and the telemetry user. `workflows` are the saved workflows with those same local keys stripped. `agents` are the user and org presets rewritten as `org` presets in the `team` pack with their ids re-derived in that namespace. `prompts` are the custom prompts as stored.
- **Import**: through the existing Import, From file (or the clipboard path): `importWorkflowText` routes a file whose `format` is `awd-team-settings` to `importTeamSettings`. The import is **adopt-only**. `planTeamSettingsImport` computes, before anything is written: the settings to adopt (only keys whose local value still equals the app default and whose incoming value does not), the workflows to add (slugs not present), the agents to add (org ids not present; an org id can never equal a user id), the prompts to add (titles not present). The confirm names it: `Adopts N settings you have not set: ...`, `Adds N workflows, N agents, N prompts.`, `Nothing you already set is changed.` A file with nothing new says so in a toast and opens no dialog. The canvas is never touched.
- **Applying** uses the app's own setters (quiet forms of `setDefaultModel` and `setEffort`, `renderDefaultDelivery`, `renderPins`, the row renderers, the switch checkboxes, `renderTelemetryFields`), then keeps the record consistent with memory (`durableRecord` needs `memoryEnabled`, OpenSpec needs the record), re-renders the saved list, agent library, palette, and prompt library, and saves the prefs once. Agents merge through `mergeImportedAgents` and prompts through `mergeImportedPrompts`, both already filtered to new entries.
- Help (`Team settings (share the shop)`) and README paragraphs describe the file, the adopt-only rule, and the intended use: commit the file to the team's fork so every new install starts from the same place.

## Why and scope

A fork for a company means ten engineers opening a blank browser each and re-entering the team's collector, defaults, and conventions, then drifting. One file fixes that, and the existing per-kind exports (workflow JSON, agent packs, custom prompts) already set the idiom; this bundles them with the shop. Adopt-only is the whole safety story: nothing the importer set is ever overwritten, nothing is deleted, and the confirm shows the exact effect first. Non-goals: a "replace mine" import mode (unpin or clear a section and import again), per-section selection on export (the importer side is safe, so the exporter sends everything), moving machine-local paths (they differ per machine by nature).
