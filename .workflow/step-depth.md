# Step depth (exhaustive steps: orchestration depth inside one step)

Context: no work item (direct session, director-proposed: should users be able to select Claude Code's multi-agent orchestration mode for a workflow or per node? Director constraints: native to the designer's architecture, intuitive, improves outcomes, and "the default should be that things work as they do today unless the user selects these modes"; director concern: would it contradict a canvas that already says which agents to spawn?). Branch: main. Status: current. Repo: agentic-workflow-designer.

## Current behavior

- A **Depth** row sits beside Effort in Node Configuration: `Standard (default) - one pass, as today` plus one option per `DEPTH_LEVELS` entry (`Exhaustive - orchestrated fan-out inside this step (Claude Code; costly; still one handoff)`); the options, the step note's label, and the load-time coercion all derive from that one list. Per step only; there is deliberately no workflow-wide switch (`nodeDepth`, `depthNodes`).
- **Unset emits nothing.** `depthHint()` is null and `depthStepNote()` is empty for every step without the value, so a workflow with no exhaustive step emits byte-identical output to before the lever existed (pinned across every preset tile and all five formats). The config key is written only when the user picks a value; `''` (Standard picked after Exhaustive) is a legitimate stored value exactly as effort stores it, so save and load are symmetric; a key never written stays absent; a foreign value becomes `''` on load (`deserializeWorkflow` is the one coercion site); the library-only normalizer (`normalizeAgentConfig`: saved and imported agents, nodes instantiated from them) never carries depth at all, and `duplicateNode` drops it too, so no creation path - saved agent, imported pack, or a canvas copy - bakes an exhaustive fan-out into a new step.
- **Emission, Claude Code formats only** (Workflow, Sub-Agents, Agent Teams; the Claude.ai skip is by design like effort, since Claude.ai has no orchestration tool): one workflow-level beat through `pushSharedHints` right after the effort hint, headed `**Depth (configured): ultracode.**` (the opt-in word Claude Code reads from the user's message - a pasted prompt is that message), naming the exhaustive steps and stating that every other step runs exactly as before, that an exhaustive step still hands off ONE result (with memory on, its helpers follow the protocol's existing dynamic fan-out naming rule `{step-slug}-{item}` so their files pool under the step on the live board; the task board and the record attribute the result to the step, never to a helper), and that depth is deliberate and expensive; plus a per-step note on the exhaustive step only, in the single-session Workflow format (its two per-step sites), where the session that holds the opt-in runs the step itself; in the Sub-Agents and Agent Teams formats the ask lives ONLY on the orchestrator's or lead's step card (`depthOrchestratorNote`: dispatch this step as an orchestrated fan-out with the step's prompt block below as the brief for every helper - that block is the brief, never a second dispatch - and, with memory on, perform the step's memory duties AS the step: its own file, `{step-slug}-{item}` helpers, task ticks, the handoff from the step's slug; with no orchestration tool, spawn it as written and let it do the same work in one session), so a spawned prompt is a plain brief and a helper is never told to fan out again: decompose, run the parts in parallel, verify every finding adversarially, synthesize, hand off one result, no new steps, never a change of who owns the next step, helpers named by the fan-out rule when memory is on - and a fallback that stands alone if the opt-in word is not recognized (do the same work in this session, say which way you ran it, one result either way). The step's own ask is the second sanctioned trigger for the orchestration tool. The workflow beat is gated on the format (not on the effort flag).
- **SDK export**: a one-line banner naming the exhaustive steps and a `# depth: exhaustive` comment on each such config; no mechanism and no opt-in word (the skeleton has no orchestration tool; the harness owner wires the fan-out); the SDK Explain rows at workflow and step level say so.
- **Guardrails**: `validateWorkflow` warns when an exhaustive step sits under a parallel node (`explainIsParallelChild`, the one fork-child predicate Explain uses) or inside a per-repository lane (the lane map is built only when a step is exhaustive, so the off-by-default feature costs validation nothing) (it would fan out again inside every branch or repository: a double fan-out); `adviseWorkflow` notes an exhaustive BUILD step by the advisor's own one builder rule (`advisorIsBuilder`: coder, frontend, backend, or a General agent holding write tools - parallel edits inside one step is where depth stops paying), and fires only when the user set it, so no preset is touched.
- **Explain**: a `Depth` row at workflow level (emitted with the hint, skipped with the lever named, by-design skip on Claude.ai) and a `Depth` row per step. Help modal section and README bullet beside Effort; the help states the preview-feature caveat: the hint states the intent, a real run is the proof.

## Why and scope

The canvas decides the shape: which steps exist, what runs in parallel, which gates loop. Orchestration INSIDE a step is a different axis - a reviewer that fans out across dimensions and verifies each finding, an audit that loops until dry, a research sweep - and it is exactly what Claude Code's orchestration mode provides. The director's worry (the canvas already says who to spawn, so this adds more agents behind the user's back) is answered by the framing: effort is reasoning depth, Depth is orchestration depth; neither adds a step, both change how hard one member works; one result, one handoff, helpers invisible. The intuitive rules: per step only (a global switch is the version that overrides the canvas), named by outcome not mechanism, a warning on double fan-out, an advisor note on a builder, Explain visibility. Scope: constants and helpers, shared hint, four per-step sites, config row, serialization, two Explain rows, SDK comments, validation warning, advisor note, help, README, one suite (presets-wide no-emission sweep, round-trip, emission per format, step-note contract, guardrails, Explain and panel). Non-goals: no thinking-keyword lever (Effort already carries that intent; two levers for one thing would disagree), no workflow-wide default, no SDK mechanism, no changes to any preset.

## Approach and decisions

- Per step, never workflow-wide (rejected: a sidebar default like Default Effort) - a global switch licenses the orchestrator to fan out anywhere, which is the form that overrides the canvas; a per-step choice is the user placing depth deliberately, the same intent the canvas expresses.
- Named Depth: standard / exhaustive (rejected: "ultracode" or "orchestrated" as the user-facing label) - named by outcome; the mechanism's word rides in the emitted prompt where it is the opt-in.
- Mirror of the effort lever (rejected: a new emission channel) - same config seam, same shared-hint beat, same per-step note sites, same Explain rows, same Claude.ai skip; nothing new in the shape of the app.
- Key absent unless touched, `''` legitimate once touched (rejected: `depth: ''` in NODE_DEFAULTS; also rejected: stripping `''` on load) - untouched and previously saved workflows keep their exact JSON, which is the literal reading of "works as it does today", and a workflow the user touched saves and loads symmetrically, as effort does.
- Guardrails instead of a thinking-keyword lever (rejected: adding an ultrathink toggle) - Effort max already carries that intent, and the keyword is read from the user's message, so it would not apply to spawned agents.
- Advisor fires only on an exhaustive BUILD step (rejected: "consider exhaustive on a lone reviewer") - the opposite nudge would nag every preset and fail the derived advisor sweep.
- The advisor keeps its own pre-existing builder rule (rejected: switching it to APPROVAL_BUILD_ROLES) - that would change existing advisor behavior (writers and testers would start drawing unreviewed-builder nags); consolidating the app's builder sets is the deferred audit already on record.
- Memory alignment, not override (the first draft said helpers "write no memory files of their own") - the memory protocol already has a dynamic fan-out naming rule; an exhaustive step's helpers follow it, so the live board pools them under the step instead of showing the step idle through the whole fan-out.
