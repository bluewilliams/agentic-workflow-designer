# Pre-registered eval: an Eval Author writes it before the plan, the Verifier executes it

Context: no work item (direct session; the director asked whether evals belong in the designer and how, then asked for the best possible build). Branch: main. Status: current. Repo: agentic-workflow-designer. Decision: an Eval Author requires a Verifier; no Tester or orchestrator stand-in.

## Current behavior

- **The role.** `Eval Author` (`evalAuthor`) joins AGENT_TYPES with a description that names the Verifier requirement, tool defaults (Read, Write, Edit, Bash, Grep, Glob, LSP), a role template, the prompt map, the OpenSpec `test` group, the Skeptic `tester` lens, and the code-search roles. It is not a build role: the approval checkpoint stays after it, so the director approves the plan with the eval in hand.
- **The template.** Independence first (requirements and repository only; ignore any plan that reaches it); what a criterion is (one observable behavior, falsifiable, pass or fail, with an exact check); coverage (every acceptance criterion, checkable constraint, implied boundary and error path, every must-not, tagged to the requirement line; ambiguity becomes a "needs a decision" criterion, never a guess); executable checks preferred (real tests in the project's conventions, tagged `eval`, expected to fail until the work exists, plus the exact command), manual procedures with exact observations where execution is impossible, rubric as the last resort; a five-step method ending in freezing the eval with a hash line; a Handoff Summary (location and hash, criteria by kind, run commands, open questions, not checkable).
- **Where the eval lives** (`evalArtifactLocation`) and who writes it: the `## Pre-registered eval` section of the durable record when one is kept, transcribed verbatim by the orchestrator from the Eval Author's handoff (the record stays single-writer; it travels with the change, and the completion gate already forbids companion documents), else `<memory dir>/eval.md` written by the author (its own memory surface), else the author's handoff carried verbatim. The executor returns its per-criterion results in its handoff; the orchestrator appends them under the eval as a dated block.
- **Who executes it** (`evalExecutorId`): the last connected Verifier in execution order (a stray Verifier with no edges never counts), memoized on the graph shape. Its step hint makes the eval authoritative (execute every criterion as written, report each PASS, FAIL, or BLOCKED with evidence or reason, in addition to its own verification and never instead of it, never edit the eval, gate verdict NOT VERIFIED when any criterion fails; one rule for a BLOCKED criterion, shared by the preamble, the executor, and the record (`evalBlockedRule`): it fails the gate when the sidebar's fail-the-run posture is on, else it is reported and does not fail the gate; results returned as a table in the handoff). The Eval Author's step hint carries its workflow-specific contract. Both hints ride the six step-hint sites every emitter already uses for verification mandates.
- **The preamble** (`evalHint`, in `pushSharedHints` for prompt, sub-agents, teams, and claude): the contract the orchestrator enforces (when the requirements are a Jira URL: the author's brief is the resolved ticket content fetched up front, child stories included for an epic, since no plan exists yet to distill it into) (brief the author with requirements and repository only, run it before any plan output, the eval is frozen, building steps may read it) and the executor by name. With no Verifier it says **Configuration error** and tells the orchestrator to stop before Step 1.
- **One click** (`addPreRegisteredEval`, Input node context menu, `Add eval`): the Eval Author lands right after the Input with the full role template in its Agent Prompt (as the presets do, so it reads and edits in place; the status line says the template is attached) (its only upstream is the requirements), the Input's edges re-route through it, and when the workflow has no Verifier a verification loop lands on the last build step (`lastBuildStepId`: the last build-role agent that can take a loop, else the last loop-free agent). Two undo steps when both happen, and the canvas re-flows through Auto Layout afterwards (the director found a hand-placed author above the row odd next to a laid-out preset); the old layout is one Undo away because Auto Layout itself takes no undo slot. `Remove eval` (on the Input or the Eval Author) first detaches any review loop on the author, removes the author, and reconnects what it sat between; the Verifier stays. The menu item's tooltip follows its state.
- **Room for a loop** (`attachReviewLoop`, generic): when anything already sits in the two slots right of the target on its row, the nodes downstream of the target slide right by 600 (a parallel sibling keeps its place), so a loop attached to a final step no longer lands on the Output node. The Eval Author itself climbs when its spot above the Input is taken, and re-routed Input edges keep their port.
- **Validation**: an Eval Author with no Verifier is an `error` with a one-click `Attach Verifier` fix (`advisorAttachVerifier`); warnings when the author has any upstream step other than the Input, when it runs after its executor, when there is more than one, and when the executing Verifier runs before a later build step (it would grade unfinished work; attach a Verifier to the last build step).
- **Record protocol** (when an Eval Author exists): a `Pre-registered eval` section (frozen hash line, numbered criteria; the Verifier appends dated `Eval results` blocks; a mismatch is a FAIL, never an edit) and a completion-gate clause (the section is byte-identical to its frozen form and its results cover this run).
- **Run report**: the directive asks for an `eval` block (`criteria`, `passed`, `failed`, `blocked`) copied from the executor's results; ingestion aggregates it per workflow (`wf.eval`); the Run Reports status line and the Tuning Prompt report the pass rate.
- **Explain**: a workflow row (`Pre-registered eval`) and a step row (`Pre-registered eval step hint`) on the author and the executor.
- Without an Eval Author every prompt is byte-identical to before (every emission is gated on the role's presence).

## Why

The value of an eval is three properties: written before the build, by a role that has not seen the plan, and frozen so the end check runs against what was asked rather than what was built. The Verifier was independent and evidence-based but derived its definition of done at the end; the Tester wrote tests after the implementation. One new role gives the first two properties; the record and the hash give the third; the existing Verifier gate gives route-back, Max Revisions, and run-report cycles for free. No Tester fallback (it would grade partly its own tests) and no orchestrator fallback (no gate to route back from). A checkbox was rejected: a step that spends a model's turns is a node you can see, configure, and route (the canvas is the job).

## Usage guidance (README and help carry it)

- Add one when the definition of done is clear and cheap to get wrong; skip it for exploration and research. It is the acceptance eval for this run's deliverable, one trial graded on outcome, not a suite over many tasks; the run-report pass rate is the regression signal.
- Practical checks happen through the Verifier's own method (curl against a local or dev instance, a browser when the Browser MCP toggle is on, a CLI with real arguments); what the environment cannot support is BLOCKED with the reason.
- The eval never widens what a run may touch: criteria belong in environments the run owns; a shared or production need is a manual procedure or BLOCKED by design, never a destructive command. The runner's permission mode and allowlist are the enforcement layer. Note: the shared Environment safety ownership block (decision 2026-09-24) has not landed; it is in the director's stash.

## Known limits

- Requirements with no executable surface get a model-graded rubric: pre-registered and build-blind, a smaller win than on code with a test runner (the role description and the docs say so).
- The Agent SDK format carries no step hints today, so it carries no eval contract either (the same gap as the verification mandates).
