## Why an eval

A workflow that builds something has to decide, at the end, whether the thing meets the requirement. Every check the designer ran before this record happened after the work existed: the Tester wrote tests after the implementation, the Verifier derived its definition of done at the end of the run, the Skeptic critiqued the plan but never defined what passing meant. Each of those is a judgment made by someone who has already seen the solution, so each drifts toward confirming the solution rather than the requirement.

Anthropic's guidance on evaluating model-generated output starts from the other end: define the success criteria first, make them specific and measurable, prefer automated and code-based grading, grade the outcome rather than the path the agent took, test both where a behavior should occur and where it should not, and make the graders resistant to the agent satisfying the grader instead of the task. The property that makes all of this work is pre-registration: the pass definition exists before the work does, written by someone who has not seen the plan, and it does not change afterwards.

The pre-registered eval brings that discipline to a single workflow run. It is the acceptance eval for this run's deliverable: one trial, graded on outcome, with the pass rate across runs flowing into Run Reports as the regression signal over time. It is not a benchmark suite over many tasks, and it does not pretend to be.

## What an eval is here

The eval is a numbered list of criteria written from the requirements alone. Each criterion carries:

- the requirement line it serves, so coverage is auditable against the source;
- its kind: **automated** (a command with an expected exit code or output), **manual** (a procedure with an exact observation), or **rubric** (a judgment against a stated bar, the last resort, with the reason it could not be made executable);
- the exact check: the command to run, or the steps to perform;
- the pass condition, pass or fail only, no partial credit.

The Eval Author walks the requirements line by line and writes at least one criterion for every acceptance criterion, every checkable constraint (a performance budget, a security rule, compatibility, data integrity), the boundaries and error paths the requirements imply (empty, zero, one, many, maximum, malformed, unauthorized, concurrent), and every must-not: the non-goals and the regressions the work has to leave untouched. An ambiguous requirement is not resolved by guessing; it becomes a criterion marked "needs a decision" and a question in the handoff.

Where the surface allows, the author writes the executable checks as real tests in the project's own conventions, tagged `eval` so they are recognizable, and records the command that runs them. Those tests are expected to fail until the work exists. The author confirms they run, never that they pass. When the requirements arrive as a Jira ticket, the resolved ticket content is the source, with every child story for an epic: an eval that covers an epic's title has covered nothing.

Then the eval is frozen: a hash line over the criteria, and no later step edits it. It lives inside the durable record, compact (one line per criterion with its check, the results as a dated block of verdicts), because one concise durable artifact is this tool's promise against the many-file spec tools. For an eval that outgrows the record, `Defaults > Eval` in the sidebar (or the Eval Author node, per workflow) moves it to a file beside the record (`<record>.eval.md`, committed with the change, a sanctioned companion on the OpenSpec-artifacts precedent); the record then carries the pointer, the hash, the counts, and one results line per run. A criterion that turns out not to match reality is reported as a failure with the reason, never fixed by rewriting the criterion. The builder may read the eval; it is the acceptance spec, and reading it is test-first, not contamination. What the builder may not do is change it.

### Example

What the Eval Author hands off for a small story ("PROJ-412: an order with an empty cart is rejected with a clear error; the cart total excludes voided lines"), transcribed by the orchestrator into the record's section:

```
## Pre-registered eval
Frozen: sha256 3f9c1a7e... (over the criteria block below)
Source: PROJ-412 (description, acceptance criteria AC1 to AC3, comment from the PO on the error wording)

- E1 [automated] POST /orders with an empty cart returns 400 and the body names the cart. (AC1)
  check: `npm test -- --grep "eval: empty cart"` (tests/orders/orders.eval.test.ts)
  pass when: exit 0; the test asserts status 400 and body.error contains "cart"
- E2 [automated] A cart with one voided line and one live line totals the live line only. (AC2)
  check: `npm test -- --grep "eval: voided lines"`
  pass when: exit 0
- E3 [automated] Must not: an order with no voided lines totals exactly as before this change. (AC2, regression)
  check: `npm test -- --grep "eval: total unchanged"`
  pass when: exit 0
- E4 [manual] The checkout page shows the empty-cart error inline, not as a page reload. (AC3)
  check: start the dev server (`npm run dev`), open /checkout with an empty cart, press Place order
  pass when: an error line appears under the button and the URL does not change
- E5 [rubric] The error wording matches the PO's comment: plain, names the cart, no stack trace. (PO comment, 2026-10-29)
  pass when: a reader unfamiliar with the code would understand what to do next
- E6 [needs a decision] AC1 says "rejected"; the ticket does not say whether a saved draft order is also rejected. Written as 400 for the live order only; the director decides whether drafts count.

Run command: `npm test -- --grep "eval:"` (E1 to E3 fail today; they execute)
Not checkable: none
```

What the orchestrator appends under the eval after the Verifier's turn:

```
### Eval results (2026-11-02 run 1)
- E1 PASS - exit 0, 1 test, body.error "Your cart is empty"
- E2 PASS - exit 0
- E3 PASS - exit 0
- E4 PASS - screenshot checkout-empty.png; URL unchanged
- E5 PASS - wording "Your cart is empty. Add an item to place an order."
- E6 BLOCKED - needs a director decision on draft orders (report-only posture: does not fail the gate)
Gate: VERIFIED (0 FAIL, 1 BLOCKED under report-only)
```

## How it follows the eval guidance

| Guidance | How this implements it |
|---|---|
| Define success criteria before building | The Eval Author runs right after the Input node, before the Planner, and the orchestrator is told to run it before any plan or build output exists. |
| Specific, measurable, falsifiable | Pass or fail only, with an exact check. The template's bar: if you cannot say what observation would make a criterion fail, it is not a criterion. |
| Prefer automated, code-based graders | Executable checks first (real tests, named commands); manual procedures with exact observations where execution is impossible; rubric last, with a stated reason. |
| Grade the outcome, not the path | Criteria describe observable behavior of the result, never which tools or steps the builder used. |
| Test where behavior should and should not occur | Must-not criteria are a required part of coverage, alongside the acceptance criteria. |
| Graders resistant to gaming | The author never sees the plan; the eval is frozen with a hash; the executor is a different role from both the author and the builder and may not edit the eval. |
| Clean, isolated environments | Criteria belong in environments the run owns (see Safety boundary); the Verifier's environment capability survey records what this environment could and could not do. |
| Honest handling of what cannot be checked | A criterion that cannot be made checkable is listed with the reason, never dropped; at execution it is reported BLOCKED with the reason, never faked. |

The honest gap between the guidance and this feature is scale. The guidance measures an agent across tens of tasks and repeated trials, with capability suites that start low and regression suites held near full pass. This feature evaluates one deliverable once. The run-report `eval` block (criteria, passed, failed, blocked) accumulates across runs so the Run Reports status line and the Tuning Prompt see the trend, which is a weak regression signal, not a suite.

## What the Verifier does with it

The eval is executed by the last Verifier the run reaches, through the gate that already exists for every Verifier loop: route-back to a chosen step, Max Revisions, run-report cycle counts. The Verifier was chosen because it already works the way an eval needs: it exercises the real system rather than reading about it.

In practice the Verifier takes each criterion as written and does what its kind demands:

- an automated criterion: run the named command, compare the exit code or output to the pass condition, and quote the result;
- an API criterion: call the endpoint against a local or dev instance with curl or an HTTP client, check status codes, response shape, and the error and edge cases the criterion names;
- a web app or UI criterion: drive the real flow in a browser when a browser-automation MCP is connected (the Browser toggle under MCP Integrations adds the live-evidence instruction), confirm the expected state renders, and capture a screenshot where it strengthens the evidence;
- a CLI or job criterion: run it with real arguments and confirm output, exit code, and side effects;
- a runbook or document criterion: follow the steps literally as a new reader would;
- a data or migration criterion: reconcile counts against the source and spot-check records.

Each criterion comes back as PASS, FAIL, or BLOCKED with the evidence or the reason. This is in addition to the Verifier's own verification, never instead of it: the eval extends the definition of done and does not narrow it. The gate verdict is NOT VERIFIED when any criterion fails. A BLOCKED criterion follows the verification posture switch the sidebar already has: under the fail-the-run posture it fails the gate like a FAIL; under report-only it is reported with its reason and does not fail the gate. One rule, stated identically in the preamble, the Verifier's brief, and the record protocol. The Verifier's results return in its handoff as a table, and the record's single writer appends them under the eval as a dated block.

## Safety boundary

The eval never widens what a run may touch. Criteria belong in environments the run owns: the working tree, an ephemeral database or container the run creates, a disposable dev instance. A criterion that would need a shared or production environment is written as a manual procedure with an exact observation, or marked BLOCKED by design with the reason, never as a destructive command. The enforcement layer is the runner's permission mode and allowlist, not the prompt: a run that cannot execute a destructive statement against a shared database cannot do it from an eval either. Note for the maintainer: the shared environment-safety ownership block (vault decision 2026-09-24) has not landed; it is in the director's stash, and the eval's executor is one more reason to land it.

## Current behavior

- **The role.** `Eval Author` (`evalAuthor`) joins AGENT_TYPES with a description that names the Verifier requirement, tool defaults (Read, Write, Edit, Bash, Grep, Glob, LSP), the role template described above, the prompt map, the OpenSpec `test` group, the Skeptic `tester` lens, and the code-search roles. It is not a build role: the approval checkpoint stays after it, so the director approves the plan with the eval in hand; the approval brief says what the author may have changed on disk before the pause (the eval itself, and test files where the surface allowed), and when the author is the only step before the pause the brief still tells the orchestrator to write the plan itself. It never owns the plan at that gate.
- **Where the eval lives** (`evalInRecord`, `evalArtifactLocation`, `evalFilePath`) and who writes it: by default the `## Pre-registered eval` section of the durable record when one is kept, transcribed verbatim by the orchestrator from the Eval Author's handoff and kept compact (one line per criterion with its check; the Verifier's results append under it as a dated block of verdicts, never a transcript). Two layers like Default Delivery choose the home: a sidebar default (`Defaults > Eval`, `state.defaultEvalHome`, shipped as the record, persisted with the prefs and carried by a team settings file when a team chooses the file) and the Eval Author node's `Eval lives in` select (`evalHome`: Default, record, or file; a portable export resolves Default). The file home is `<record>.eval.md` beside the record, committed with the change; the record then keeps the pointer, the hash, the counts, and one results line per run, and the completion gate sanctions the file and checks its hash. The durable surfaces stay single-writer either way.
- **Open questions** (`EVAL_AMBIGUITY_OPTIONS`, `evalAmbiguityOf`, `evalAmbiguityStepClause`, `evalAmbiguityOrchestratorClause`): what the author does with a question the requirements leave open, a per-node select on the Eval Author (`config.evalAmbiguity`, no sidebar layer, as Defect Posture). `bar` (default): decide and record what it can defend, ask the director only when a wrong answer would fail work that meets the requirements or pass work that does not. `always`: every open question to the director before the freeze. `decide`: never interrupt, assumptions recorded as decisions. The author's step hint carries its clause; the orchestrator preamble carries the matching handling (one batch of questions before the freeze and before planning, answers returned to the author to finalize and freeze, each recorded as a decision and folded into the planning step's brief as a resolved requirement, as the clarify gate does; non-interactive runs adopt the proposed defaults and record them). The preamble also binds the orchestrator to the freeze: every later brief is written toward the eval, never around it; a criterion that looks wrong is reported as a mismatch and fails the gate, and only the director can move the bar, as a recorded decision. The template gained a "Pin only what the requirement states" paragraph from the backtest: no literal phrases, counts, file lists or orderings the requirement does not state; no criterion that only restates others; structural assumptions named in the check; must-not criteria tagged as guards. Without a record the choice does not apply, and both selects hide with the record toggle (`syncEvalHomeUI`, as the artifact path and OpenSpec fields do; the stored choice stays sticky): the eval goes to `<memory dir>/eval.md`, written by the author; else the author's handoff is carried verbatim into the executor's brief.
- **Who executes it** (`evalExecutorId`): the last Verifier that belongs to the run, in execution order. Belonging means connected to an Input node by any chain of edges in either direction (`evalReachableIds`), deliberately weaker than forward reachability so a hand-built gate's forward No branch counts as the run (every generator emits it) while a loose node or a disconnected sub-chain does not; with no Input node, any node that has an edge. Memoized on the graph shape.
- **The preamble** (`evalHint`, in `pushSharedHints` for the prompt, sub-agents, teams, and claude formats): the contract the orchestrator enforces (brief the author with requirements and repository context only, run it before any plan output, the eval is frozen, building steps may read it; for Jira requirements, the author's brief is the resolved ticket with child stories for an epic) and the executor by name with the blocked rule. With no reachable Verifier it says **Configuration error** and tells the orchestrator to stop before Step 1: an eval nobody runs is worse than none.
- **Step hints** (`evalStepHint`, on the six emission sites the verification mandates use): the author's workflow-specific contract, and the executor's clause described above.
- **Route of the one-click Verifier's gate** (`EVAL_FIX_ROLES`, `evalRouteBackTarget`, `attachEvalVerifier`, 2026-11-01): the loop wraps the last build step so the eval runs after the deliverable exists, and on the Feature presets that is the Tester, which cannot change what the eval failed; so the gate's No edge starts pointed at the nearest upstream step that changes the deliverable (the build roles minus the Tester: the Implementer on Feature Development, so a failure re-runs fix, review, test, verify), the last one in execution order when several qualify, and the fork when that step is one branch of a parallel group (a direct child of a fork with more than one agent branch), so a failure in any branch re-runs the whole section; when the wrapped step changes the deliverable itself or nothing upstream does (a research workflow ending in an Analyst), the wrapped step keeps the route. Since the same evening the rule belongs to every Verifier loop (verifier-and-review-loop-family: `verifierRouteBackTarget`, `attachVerifierLoop`), the menu's Add verification included; presets are hand-wired and keep their routes. The toast names the route and the gate's dropdown changes it in one click.
- **One click** (`addPreRegisteredEval`, Input node context menu, `Add eval`): the Eval Author lands right after the Input with the full template in its Agent Prompt, the Input's edges re-route through it (the Input keeps its port), and when the run has no Verifier a verification loop lands on the step chosen by `lastBuildStepId`: the last build-role agent in the run; if that step already carries a loop, the first loop-free agent downstream of it (a parallel sibling never qualifies); if nothing runs after it, none, and the toast says so. The author remembers the Input edges it replaced (`evalReplaced`) so Remove restores each one with its own label and port. The canvas then re-flows through Auto Layout; the old layout is one Undo away. `Remove eval` (on the Input or the Eval Author) detaches any loop on the author, removes it, restores the Input's edges from memory, and re-points a gate's No edge that targeted the author to one successor (a gate has one revise edge); the Verifier stays.
- **Room for a loop** (`attachReviewLoop`, generic): when anything already sits in the two slots right of the target on its row, the nodes downstream of the target slide right far enough to clear the new gate; a parallel sibling keeps its place.
- **Validation**: an Eval Author with no reachable Verifier is an `error` with a one-click `Attach Verifier` fix when a suitable step exists (`advisorAttachVerifier`); warnings when the author has any forward upstream step other than the Input, when it runs after its executor, when there is more than one, and when a build step in the run does not finish before the executor (downstream of it or alongside it in a parallel branch). The validator sorts the graph once and reuses one connectivity set.
- **Record protocol** (when an Eval Author exists): the eval file is written and frozen; the record's `Pre-registered eval` section holds the pointer, the hash, the counts, and one results line per run; the Verifier's per-criterion results are appended to the eval file as dated `Eval results` blocks; a mismatch is a FAIL, never an edit; the blocked rule. The completion gate sanctions the eval file as a companion, checks it still matches its hash, and checks the record carries this run's results line.
- **Run report**: the directive asks for an `eval` block copied from the executor's results; ingestion aggregates it per workflow, ignoring an empty block, an array, or a block whose parts exceed its total or carry non-integer counts (a null count reads as zero); the Run Reports status line and the Tuning Prompt report the pass rate.
- **Explain**: a workflow row (`Pre-registered eval`) and a step row (`Pre-registered eval step hint`) on the author and the executor.
- Without an Eval Author every prompt is byte-identical to before: every emission is gated on the role's presence.

## Usage guidance

The README and the help modal carry this. Add an eval when the definition of done is clear and cheap to get wrong: a feature with acceptance criteria, an API, a CLI, a migration. Skip it for exploration and research, where the deliverable is understanding rather than behavior. Expect one more step before the planner, plus a Verifier on workflows that lack one. Read the Verifier's BLOCKED reasons: they say what this environment could not prove, which is the most useful line in the report.

## Known limits

- Requirements with no executable surface get a model-graded rubric: pre-registered and build-blind, a smaller win than on code with a test runner.
- One deliverable, one trial. The run-report trend is the only cross-run signal.
- The Agent SDK format carries no step hints, so it carries no eval contract either (the same gap as the verification mandates).
