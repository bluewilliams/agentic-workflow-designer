# Plan approval gate (Approve plan before build)

Context: no work item (direct session, director-proposed: "an off by default option which presents the reviewed plan to the director before the orchestrator starts implementing... the director would always need to approve the high level plan or make modifications before the implementation starts"; then "please do your absolute best to ensure this cannot break anything, and make it the best it can possibly be"; and "not all workflows have a planner or a skeptic"). Branch: main. Status: current. Repo: agentic-workflow-designer.

## Current behavior

- A sidebar toggle **Approve plan before build** (`approvePlanToggle`, `state.approvePlan`, persisted in `awd_prefs` like `clarifyFirst`, reset by New Workflow) sits under Clarify requirements first; both carry the `.run-gate-toggle` rule (one per line - the memory-toggle flex rule is scoped to the memory section, so the two labels had wrapped side by side). Off by default.
- **The checkpoint is resolved statically from the canvas** (`approvalCheckpoint()`): the first agent step in topological order over the SAME agent list every generator emits (unreachable palette nodes included - the generators run them, first in fact, so the director approves before them too), whose role changes files or produces the deliverable (`APPROVAL_BUILD_ROLES`: coder, frontend, backend, writer, tester, general - a General agent may do anything and pausing before it is the safe direction, with no tool consultation; a missing or retired role id classifies as General too, as the rest of the app treats it; every other role is classified as read / judge / advise, pinned by test; memoized on the structural signature so keystroke-driven regeneration sorts once per canvas shape). Everything before it IS the plan: a Planner and its Skeptic gate where the shape has them, an Investigator in Bug Fix, nothing in a single-builder shape (then the orchestrator writes a short plan itself). A research or analysis run that ends in a Writer checkpoints before the Writer (research in hand); a shape with no file-changing or deliverable-producing step at all (a pure review) checkpoints before its FIRST step, so the director approves the approach. A checkpoint that falls inside a per-repository lane moves to the lane's FIRST step: one approval covers every repository, and every format pauses at the same place (the SDK fans the lane out as one unit); the gate names the moved pause as "the first step of the per-repository lane that will build" (a third wording, since the lane opener itself may not build) and never claims the workflow builds nothing. The sibling set (`approvalSiblingIds`) is the one definition of "runs alongside" for the markers and the SDK hook; its fork lookup picks the LAST parallel parent in topological order, the way the generators' fork maps do. An empty canvas emits nothing. `prior` is every step that completes before the pause and never a sibling that runs alongside the checkpoint (those wait with it and carry the marker; a mutual wait is impossible by construction). The memo holds IDS (node, prior, group, owner, reviewer, ownerGroup) and re-resolves every field to LIVE nodes through one index per call (callers never juggle ids and objects); generators resolve the checkpoint ONCE per generation and pass it to the gate hint and every per-step site (`approvePlanHint(cp)`, `approvePlanStepHint(node, cp)`), so a regeneration costs one signature build per format, not one per agent; the lane-move lookup reads the per-repo lane map once per resolve (undo, redo, and re-import replace objects under the same ids), keyed on the shared `graphShapeSig(true)` (ids, types, strategies, decision No labels, labeled edges, plus roles and review-loop attachments - the lane map keys on the structural part only) that the per-repo lane map also uses.
- **The gate** (`approvePlanHint()`, emitted through `pushSharedHints` after Clarify-first, so all four prose formats get it from one source; the SDK renders it as a comment banner): the orchestrator runs the checkpoint ONCE, before the named step, and only after every prior step completed including any Skeptic gate; presents a BRIEF (approach, files or artifacts, risks, out of scope, options that lost) readable in a minute; asks ONE question and waits for one of THREE answers: approve; modifications (bounded changes that keep the approach - authoritative, applied to plan and task list, recorded in the durable record as decisions when a record is kept, never relitigated with a Skeptic, approved parts never re-opened); or rejection with direction (the approach changes - it goes back to the step that OWNS the plan, resolved once in `approvalCheckpoint()` as the last prior step whose role owns plans (`APPROVAL_PLAN_OWNER_ROLES`: planner, architect, debugger), else the last prior step that is not a review node (`approvalIsReviewNode`: an attached review loop OR a hand-wired Skeptic / Verifier (`isReviewRole`, the one predicate the review machinery's three sites now share) / Reviewer from the palette), so a Researcher or Code Reviewer between the Planner and the builder never becomes the owner and named in the gate; when that owner sits in an `all` parallel group the gate names the whole group and says re-dispatch all of them (the SDK re-gathers it), as authoritative input; the owner revises, the review node attached to it (or the first HAND-WIRED Skeptic / Verifier that followed it - a loop attached to another step never reviews the plan, and a Code Reviewer is never promoted to the plan gate) re-runs scoped to the change; when prior steps exist but none owns a plan, the gate says so and the orchestrator revises itself (never "no step ran") (the gate names its role: Skeptic gate, Verifier gate), and the brief returns for approval; at most three rounds, after which the run STOPS and records the unresolved rejection: nobody builds what the director refused); fires once per approval (a revise loop returning to the step never re-asks); non-interactive runs never block (the unapproved plan is recorded as an explicit risk). Memory on: the wait and the answer are logged (the kickoff creates the file; run it first if it has not run) as orchestrator log lines in `shared.md` (the live monitor shows both). Telemetry on: a `gate.verdict` event with step `director-approval`, status pass or revise.
- **A per-step marker** (`approvePlanStepHint(node)`) lands on the checkpoint step AND on every step that runs alongside it under the same parallel fork, at all six prose per-step sites; the marker carries its own contract (the orchestrator runs the approval and dispatches the step only after it passes), because a Sub-Agents file never sees the orchestrator's gate (Workflow single and parallel, Sub-Agents, Agent Teams, Claude.ai single and parallel), so the orchestrator cannot start that step early even if it skims the preamble.
- **The SDK export is a real pause**: a `def _awd_approve_plan(brief) -> (text, kind)` helper (console prompt; `sys.stdin is None or not sys.stdin.isatty()` guard plus an `EOFError` catch - no TTY or a closed input returns `unattended`, never blocks or crashes; it classifies the reply honestly: empty / approve / yes / ok / lgtm are approvals; `^reject(ed)?\b` is a rejection with the rest as direction, with or without a space before the colon; a plain refusal - no, nope, stop, do not build this - or a bare `reject` asks ONCE what should change through one `_awd_ask_direction()` helper and becomes a rejection with that direction, or `stop` when none is given; anything else is a modification; the helpers carry an `_awd_` prefix no step label can produce, so a step named Approve Plan never shadows them; the script has no briefing step, so the helper is labeled as showing the FULL output of the steps so far, where the prose formats ask the orchestrator for a brief). **Every step that runs before the checkpoint group is emitted ONCE as `async def _awd_plan(_awd_ctx)`**: the generator's own loop output for that stretch, written on `_awd_ctx` from its first line (the loop's starting context variable is `_awd_ctx` whenever a plan stretch exists) and re-indented by four spaces - indentation is the only post-processing, no emitted text is rewritten - returning the stretch's last result. The run calls `_awd_plan(requirements)` first; a rejection calls it again with the requirements, the rejected attempt, and the direction riding in on `_awd_ctx`, so every shape the loop can emit (sequential steps, all / any / race groups, per-repo lanes, review loops) is re-runnable through the same code that ran it first, and there is no second step emitter to keep in sync. The answer loop runs at most three rounds and the third rejection raises `SystemExit` BEFORE any revision; a `stop` answer stops at once; a checkpoint with no step before it stops on a rejection with the direction in the message (nothing can revise an unwritten plan). The checkpoint step runs with `context=_approved` (the brief, plus the modifications when the kind is modify, plus an explicit unapproved-plan risk sentence when unattended). Once, never per lane. The SDK banner states what THIS script does where it differs from the prose contract above it: the hook reads the console and writes no shared.md line and no telemetry event (those are the prose orchestrator's duty; add them to a custom hook if the monitor should see the wait), and a rejection re-runs every step before the checkpoint as one unit where the prose formats re-dispatch only the plan owner and what follows - simpler and always re-runnable, at the cost of repeating research or lanes that precede the plan, at most twice. The director weighed the SDK depth against the clarify-first precedent (a comment banner there) and kept the full design.
- **Explain** gains a `Plan approval gate` row naming the checkpoint step (emitted / skipped), deep-linked to Requirements, and a per-step `Director approval checkpoint` row so the marker is accounted for like every other per-step hint. Help modal section and README paragraph document it; the toggle tooltip carries the contract.

## Why and scope

The Skeptic proves a plan is internally sound; only the director knows whether it is the right plan. Today that judgment lands after the build, in review, when it is expensive. OpenSpec users already expect a human approval between proposal and apply. The option is off by default so the friction reduction the director values is untouched. It is a sibling of Clarify requirements first (same kind of toggle, same gated emission through the shared hint preamble), never a per-node input. Scope: one state field, prefs save/restore/reset, one checkbox, checkpoint resolver, gate hint, per-step marker at seven sites, SDK banner + helper + hook, Explain row + section link, help section, README paragraph, eleven tests. Non-goals: no new node type, no monitor UI (the memory log lines already surface the wait), no second approval unless the director asks.

## Approach and decisions

- Checkpoint by deliverable-producing role, not by planner presence (director: "not all workflows have a planner or a skeptic") - anchoring on the first builder makes the rule total: every shape has a well-defined pause, and whatever ran before it is the plan.
- Static resolution named in the prompt (rejected: "pause before implementation" left to run-time judgment) - the orchestrator gets the step by name in the gate AND a marker on the step, so there is no ambiguity about where the pause lands.
- Brief, not plan (rejected: presenting the full plan) - a director reads a minute, not a page; the plan itself stays where the steps wrote it.
- Modifications authoritative and never relitigated (rejected: re-running the Skeptic on modified plans) - the director outranks the Skeptic, and a second gate would turn approval into a loop.
- Three answers, not two (director: "if the user rejects the plan and gives feedback does the workflow just start over from planning again?") - modifications the orchestrator applies itself would skip the Planner's craft and the Skeptic's scrutiny when the APPROACH changes, so a rejection with direction re-dispatches the plan owner and re-runs the Skeptic gate; three rounds bound the loop and a third rejection stops the run instead of building what was refused.
- Fires once per approval (rejected: re-approval on every revise cycle) - revise loops are the reviewer's mandate on top of the approved plan; a second approval only when the director asks.
- SDK hook is real code with a no-TTY guard (rejected: comment only) - the pipeline format can actually pause; non-interactive runs never hang, which is the same doctrine the clarify gate states in prose.
- Shared-hint emission (rejected: per-format copies) - one source, four formats, the parity tests hold by construction.
